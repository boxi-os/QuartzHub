6.8 – GitHub Pages

6.8 – GitHub Pages

13. Nov. 20262 Min. Lesezeit

GitHub Pages serves a site from a branch of a repository, free and over https. QuartzHub puts the build as one commit onto a branch of its own, usually gh-pages, and points Pages at that branch. GitHub Actions are not needed.

Setting it up once

  1. Token: under Settings ▸ Connections, enter a personal access token with the “repo” scope (6.7).
  2. Repository: under Git Sync ▸ Create a repository on GitHub. On a free account it has to be public (6.5).
  3. Base URL: under Configuration ▸ Site, enter the future address, usually name.github.io/repository, or your own domain.
  4. Target: under Publish, a new target of the type Git branch, Provider GitHub Pages, Branch gh-pages. The branch must not be the one the project itself stands on.
  5. Switching Pages on: in the GitHub Pages section below the target, Point at “gh-pages”.

Then build and Publish now (6.12). A few minutes later the site is at the address the section names.

The GitHub Pages section

It shows whether Pages is Published, Building, Failed or Never built, the site’s address and which branch it comes from. Reload status asks GitHub again.

Custom domain: such as wiki.example.org. At the domain’s provider, a DNS entry has to point at GitHub; GitHub describes how. Save settings writes the domain; GitHub puts it as a file CNAME into the branch, and QuartzHub keeps it at every publish. Enforce HTTPS only works once GitHub has issued the certificate, a few minutes after setting the domain.

What happens on publishing

The branch is replaced entirely by the current build every time (force push), in a single commit without history. That is why QuartzHub asks first. If nothing changed, nothing is uploaded. The project’s hooks do not run.

Codeberg Pages serves the branch pages the same way. GitLab additionally needs a CI job that serves the files; the branch alone publishes nothing there.
